# 3. 账号、联机、计时与回放

[返回教程](README.md) · [上一章](02-studio-workflow.md) · [下一章](04-audio-and-video.md)

本章描述案例的设计和修复经验，不等同于服务端安全审计。下面的数据字段为理解用途的简化示意，不是可直接部署的完整数据库定义。

## 称呼、UID、登录码各司其职

首次进入要求输入称呼，显示在大厅和排行榜。称呼可以重复或更改，因此另用公开UID识别玩家：从五位数字开始，例如10000起步，分配空间用满后自然增加一位。服务端应保证唯一分配与并发安全，不能由客户端随机猜一个五位数。

登录码用于恢复账户，属于秘密凭据。案例采用大小写字母和数字组成的17位代码，末位用于输入校验。校验位只能帮助发现输错，不会替代身份验证；不要把它显示到排行榜、在线玩家或回放公开信息里。实现还应考虑随机性、服务端保存方式、尝试频率限制及遗失恢复流程；这些不能仅凭UI正常就宣称安全。

案例中通过界面创建账户并恢复同一身份，UID保持一致；排行榜响应检查没有公开秘密凭据。没有测试UID空间耗尽或高并发分配，教程不将其列为实测通过。

## 对局状态要有清楚的生命周期

```text
等待双方 → 3秒准备 → 正式对战 → 胜/负/平 → 结算与存档
```

示意字段：

```text
roomCode, round, phase, players, bombs, fires
readyUntil, startedAt, deadline, winner
rulesVersion, initialState.obstacles, events
```

准备期不能只遮住屏幕：引擎也必须拒绝移动、落子，AI同样不能行动。设正式开始时刻为 `readyUntil`，截止时刻为 `readyUntil + 120000`。显示倒数、计算胜负和服务端结算应围绕同一时间语义。

联机共享准备截止时刻；刷新页面不能再免费获得完整三秒，也不能延长正式对局。服务端返回剩余时间时要考虑客户端时钟偏差。仅修改客户端预览不代表云端逻辑已经更新：本案例就出现过云函数要等Studio轮次结束后才部署的时间差。

## 真实踩坑：重开一局，立刻0:00

早期练习总使用相同房间身份和 `round=1`。服务端为保证幂等，重复开局会返回旧记录及旧截止时间；用户返回首页几分钟后再进入，旧deadline已过，便立刻结算。

修复思路是同时保留两个语义：

- **真正的新局**：创建独立对局身份，获得新的准备期与120秒。
- **同局重连或重复请求**：沿用原记录和截止时间，不能借刷新续时。

分别测试“返回大厅再开”“结算后再来一局”“刷新后开始”；看实际新纪录及时间，而不是只看重开按钮是否可点击。

## 大厅、排行和延迟

大厅展示在线玩家及空闲/对战状态，并列出正在进行的对局。排行榜显示胜局、负局及胜率；平局不改变积分。胜率是否把平局计入分母需要在项目中明确，本文不凭惯例替实现补定义。

双方延迟用毫秒表示，应标明测量含义。往返时延RTT不能直接称作端到端输入延迟；后台页节流、暂时失联或没有采样时，不应把未知值显示成0ms。案例已有相关显示，但尚无广泛弱网和跨地区实测结论。

## 回放不是一段操作说明文字

记录初始状态、规则版本、双方动作与时间，以及必要的随机种子。重放时从同一初始状态按顺序执行事件，再检查结果一致；不能只录按键而漏掉地图、随机条件或版本差异。

新增中路障碍后，当前对局保存八格地图。旧记录缺少地图快照时回退到六格旧地图，避免旧角色走过的位置现在突然出现障碍。此兼容只说明本次地图变更得到处理，不能据此推断任意未来规则变更都已自动兼容。

回放可另渲染到Canvas并用浏览器支持的录制方式导出视频。检查实际下载文件是否可播放、时间是否前进、画面是否完整；一个“导出成功”提示不构成验收。浏览器导出格式兼容性应单独记录，不将某台Chromium的WebM成功外推到所有手机。

## 0.15.2：公开观战、战绩与失效会话

大厅列出进行中的房间，观众可从公开列表进入，不必先向玩家索取房间码。公开观战应只读，不占玩家座位，也不能替玩家发出操作。玩家战绩与回顾使用公开资料；登录码、会话令牌与恢复凭据不得混入列表响应。

测试数据清空后，旧设备可能仍保存已失效的账号。最新实现进入时校验一次会话，心跳遇到明确 401 也清理本地失效状态并提示重新注册；暂时网络错误保留登录状态。在线列表来自真实心跳，空列表不应用虚构玩家填充。

回放导出依次检测 MP4/H.264 和 WebM 候选 MIME 类型，实际创建编码器成功后才录制。文案应写“优先 MP4，兼容回退 WebM”，不能保证所有浏览器都能输出 MP4。
