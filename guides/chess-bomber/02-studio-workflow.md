# 2. 在同一 Studio 工程里迭代

[返回教程](README.md) · [上一章](01-rules-and-plan.md) · [下一章](03-state-and-services.md)

## 一轮任务怎样提交

打开自己已有的 Studio 项目，先读当前对话要求、已有预览与版本记录。把本轮最小目标、复现步骤、预期结果和保留功能一起写进消息输入框；需要资源时通过附件上传。发送后等待本轮完成，再检查预览、测试结果和版本。

本案例持续修改同一工程，保存历史轮次。不要遇到一个输入问题就重新创建工程，否则账户、后端和历史记录容易分裂。用户已经指定“让Studio修改、由操作者测试”时，遵循这个分工。

一条有效修复指令通常包含：

```text
问题：按住方向时，第二根手指按落子没有反应。
复现：保持第一触点 → 第二触点落子 → 抬起第二触点 → 再落子。
预期：两枚炸弹成功放置，第一触点不失效，抬指不重复触发。
边界：保持一次按键走一格，不改变现有规则、账号与布局。
验收：横屏和竖屏执行；区分网页模拟与实体手机。
```

原始抱怨提供方向，复现步骤让修复变得可验证。每轮尽量解决同一类问题；音乐与地图可以分别提交，不把难以归因的十几个变化混在一次验收里。

## 布局：以可用空间为依据

本案例出现过方向键过低、底部裁切、已横屏仍提示横屏等问题。处理时不要只看设备方向标签，要看实际可用视口：浏览器工具栏、安全区、键盘和嵌入预览都可能减少高度。

竖屏采用掌机布局：上方状态和棋盘，中间选弹，下方左方向键、右落子键。横屏把状态和操作分配到棋盘两侧。适配依据应是控件能否完整显示、能否实际点击，而不是“看起来像手机”。

后续增加静音和账户按钮时，首页320宽又出现标题逐字竖排、账户按钮越界。修复为标题不拆行、工具组允许换到下一行、长昵称省略。**新功能也会破坏已通过的布局，需要针对新增控件回归。**

## 多点触控：每根手指有自己的状态

方向、选弹、落子使用独立的 `pointerId` 跟踪。处理 `pointerdown`、`pointerup`、`pointercancel`，避免任意一次抬手清空全部触点。需要阻止页面手势的区域设置合适的 `touch-action`，不要无区别关闭整个网页的正常交互。

本案例让指针按下立即执行，同时避免随后 `click` 再执行一遍；键盘与辅助操作仍保留有效入口。静音按钮也不能抢走空格焦点，导致本该放弹的空格只切静音。

两个常见误判：

- 连续自动点击“移动、落子”只能证明顺序输入，不能证明同时双指。
- 自动化工具的触点参数含义需要按实际事件核实。本案例曾因误解触点结束参数，让测试脚本自己造成假失败；最终依据指针日志修正了脚本。

## 视觉范围与实际范围一致

角色棋子、炸弹和障碍必须在轮廓或颜色上区分。炸弹、火焰尺寸从当前格距派生，不用固定大像素：同一个大炸弹放进小棋盘，会看似覆盖两三格而实际只伤害一格。

定位与动画分两层：外层负责格点坐标与半格居中，内层负责缩放或脉冲。不要让动画里的 `transform` 覆盖外层平移；本案例手机火焰偏移就是这类问题。

验收时同时量格距与火焰尺寸，观察爆炸瞬间角色是否因实际危险格死亡。图标清楚不代表伤害正确；伤害正确也不代表视觉可信。

## 规则改动必须到达所有使用方

爆炸规则应来自同一计算函数，供伤害、AI危险图和需要的范围提示复用。车从“能穿障碍”修成“立即停止”后，也要更新帮助说明与测试，不只改一句文案。

对地图这类影响回放的变更，保存每局地图快照并更新规则版本。具体做法见下一章。

## 后续修订：危险范围与公开功能

危险提示复用 dangerMap，避免另写一套与伤害判定不一致的范围算法。半透明填充按格距缩放，位于棋盘线上、棋子与角色下；提示层不拦截指针事件。验证普通爆炸、连锁、车遇障碍停止和炮只穿一个障碍。

公开观战、玩家战绩、视频导出与会话恢复需要分别验收。维护状态解除后，带旧维护时间的设备也应直接回到正常流程。
